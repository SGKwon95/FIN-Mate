# 면접 모범 답변 (카테고리 1~4)

---

## 1. FIN-Mate 프로젝트

### RAG 파이프라인

---

**Q. pgvector를 선택한 이유?**

금융 데이터는 외부 전송이 민감해서 온프레미스 환경을 유지해야 했습니다. Chroma나 Qdrant는 별도 서버가 필요한데, 이미 PostgreSQL을 메인 DB로 쓰고 있어서 pgvector 확장만 추가하면 인프라를 늘리지 않아도 됐습니다. 또 금융 거래 데이터와 벡터 데이터를 한 트랜잭션 안에서 다룰 수 있다는 점도 장점이었습니다. 스케일이 커지면 전용 벡터 DB를 고려하겠지만, 이 프로젝트 규모에서는 pgvector가 적합한 선택이었습니다.

---

**Q. 계층 구조 청킹을 선택한 이유?**

금융 약관은 "제5조(중도해지) ① 가입 기간에 따라..."처럼 조-항 계층이 명확합니다. 고정 길이로 512토큰씩 자르면 "제5조" 제목과 실제 내용이 다른 청크로 분리되거나, 여러 조항이 섞이는 문제가 생깁니다. 그러면 "중도해지 패널티"를 검색했을 때 관련 없는 조항이 함께 검색됩니다. 계층 구조로 분할하면 청크 하나가 하나의 조항 또는 한 항에 대응되고, 항으로 분할할 때는 조 제목을 prefix로 붙여서 "제5조 ①"처럼 문맥이 유지됩니다.

---

**Q. Hybrid Search 도입 계기와 효과?**

순수 벡터 검색은 의미 유사도 기반이라 "중도해지 패널티 비율이 몇 퍼센트야?"처럼 키워드가 중요한 질문에서 약했습니다. 의미적으로 유사한 문장을 가져오더라도 정작 "비율", "퍼센트" 같은 핵심 키워드가 포함된 청크를 놓치는 경우가 있었습니다. BM25는 키워드 직접 매칭이 강하지만 "적금 해지하면 어떻게 돼?"처럼 문맥 이해가 필요한 질문에서는 약합니다. 두 결과를 RRF로 결합하면 어느 방식으로든 상위에 랭크된 청크가 최종 상위로 오기 때문에 두 유형 모두 안정적으로 처리할 수 있습니다.

---

**Q. RRF k=60 기준?**

k=60은 Cormack et al. 2009 논문에서 제안한 기본값입니다. k값이 작을수록 상위 랭크에 민감해지고, 클수록 랭크 차이가 희석됩니다. k=60은 상위 결과는 충분히 보상하면서 하위 결과의 영향을 줄이는 균형점으로 알려져 있고, 실제로 여러 IR 벤치마크에서 검증된 값이라 그대로 사용했습니다. 프로덕션이었다면 도메인 데이터로 튜닝했겠지만, 이 프로젝트에서는 표준값이 충분히 합리적이었습니다.

---

**Q. quality_score vs Cross-encoder?**

Cross-encoder는 쿼리와 각 청크를 쌍으로 묶어 재점수를 매기는 방식인데, 로컬 환경에서 매 요청마다 top-K 청크에 대해 모델 추론을 돌리면 Latency가 크게 늘어납니다. 온디바이스 LLM이 이미 GPU 자원을 쓰고 있어서 추가 추론 부담이 부담스러웠습니다. quality_score는 사용자 피드백(👍/👎)을 청크별로 누적해서 벡터 유사도 정렬 시 가중치로 적용하는 방식입니다. 실시간 추론 없이도 "이 청크가 과거에 좋은 답변을 만들었다"는 정보를 검색에 반영할 수 있습니다. 다만 피드백이 쌓이기 전까지는 효과가 없다는 한계가 있습니다.

---

**Q. 캐시 임계값 0.95 기준?**

금융 정보는 미묘한 차이가 큰 영향을 줍니다. "정기예금 중도해지 이율"과 "정기적금 중도해지 이율"은 임베딩 유사도가 꽤 높지만 답변이 달라야 합니다. 0.9 정도로 낮추면 캐시 히트율은 올라가지만 다른 상품의 답변이 반환될 위험이 있습니다. 0.95는 사실상 "거의 동일한 질문"에만 캐시를 쓰겠다는 보수적인 기준입니다. 캐시보다 정확성이 우선인 금융 도메인에서는 이 트레이드오프가 맞다고 판단했습니다.

---

**Q. Hallucination 방지 프롬프트 설계?**

세 가지를 적용했습니다. 첫째, 시스템 프롬프트에 "Context에 없는 수치는 추측하지 말고 '제공된 약관에서 확인되지 않습니다'라고 답하라"고 명시했습니다. 둘째, temperature를 0.05로 낮춰 창의적인 생성을 억제했습니다. 셋째, 약관 조항 인용을 필수로 요구해서 "(제5조 ③항에 의거)"처럼 근거를 명시하도록 했습니다. 근거 없이 말하면 잘못됐다는 걸 사용자도 바로 알 수 있습니다.

---

**Q. RAGAS 지표를 어떻게 자체 구현했나?**

RAGAS 라이브러리를 쓴 게 아니라 같은 지표명을 차용해서 LLM-as-judge 패턴으로 직접 구현했습니다. 평가 LLM(Qwen2.5-14B)에게 질문·컨텍스트·답변을 주고 각 지표를 1~5점으로 채점하도록 프롬프트를 작성한 뒤, 0~1로 정규화해서 Arize Phoenix에 어노테이션으로 전송합니다. Context Relevance는 "검색된 컨텍스트가 질문과 얼마나 관련 있나", Faithfulness는 "답변이 컨텍스트 내용에 충실한가", Answer Relevance는 "답변이 질문에 직접적으로 답하는가"입니다. 공식 RAGAS와 점수 절대값은 다를 수 있지만, 상대적인 품질 추이를 모니터링하는 데는 충분합니다.

### Kafka 타행이체

---

**Q. 9단계로 나눈 이유?**

실제 공동망(KFTC) 구조를 모사했습니다. 이체 요청 → 게이트웨이 수신 → 라우팅 → 타행 전달 → 타행 처리 → 결과 반환 → 게이트웨이 수신 → 정산 요청 → 정산 완료의 흐름입니다. 각 단계를 별도 Kafka 토픽으로 분리한 이유는 각 참여자(FIN-Mate, 공동망 게이트웨이, 타행 시뮬레이터)가 독립적으로 실패하고 재시도할 수 있어야 하기 때문입니다. 모놀리식으로 구현하면 중간 단계 실패 시 전체를 재처리해야 하지만, 토픽으로 분리하면 실패한 단계부터 재처리가 가능합니다.

---

**Q. at-least-once를 선택한 이유?**

Exactly-once는 Kafka 트랜잭션과 idempotent producer 설정이 필요하고 성능 오버헤드가 있습니다. 금융 이체는 중복 처리가 생기면 안 되지만, 그 보장을 Kafka 레벨에서만 할 필요는 없습니다. DB에 idempotency key(transferId)를 두고 이미 처리된 키가 들어오면 무시하도록 설계하면, at-least-once로 메시지가 중복 전달되더라도 실제 이체는 한 번만 일어납니다. 애플리케이션 레벨 멱등성으로 처리하는 게 더 유연하고 이해하기 쉽습니다.

---

**Q. 브로커 2개 동시 장애 시?**

RF=3, min.insync.replicas=2 설정에서 브로커 2개가 동시에 내려가면 ISR이 1개만 남아 min.insync.replicas 조건을 충족하지 못하므로 Producer 쓰기가 실패합니다. 즉 메시지 유실 없이 서비스가 중단됩니다. 유실보다는 중단이 낫다는 판단입니다. 금융 시스템에서 잘못된 이체가 처리되는 것보다 일시적으로 이체가 안 되는 게 훨씬 낫기 때문에 이 설정이 맞다고 생각합니다.

---

**Q. 자행/타행 처리 방식을 분리한 기준?**

자행 이체는 같은 DB 안에서 출금 계좌와 입금 계좌를 동시에 업데이트하면 되므로 DB 트랜잭션 하나로 원자성을 보장할 수 있습니다. 굳이 Kafka를 거칠 이유가 없고 오히려 Latency만 늘어납니다. 반면 타행 이체는 외부 시스템(공동망, 타행)과 통신해야 해서 동기 방식이면 네트워크 지연이나 외부 시스템 장애가 직접 사용자 응답에 영향을 줍니다. 비동기로 분리하면 요청 접수와 실제 처리를 분리해서 사용자는 즉시 응답을 받고 처리는 백그라운드에서 진행됩니다.

---

**Q. DB 행 락 병목을 어떻게 발견했나?**

k6로 500 VU를 동시에 발생시켰을 때 처리량이 예상보다 낮고 Consumer 처리 시간이 튀는 현상이 있었습니다. PostgreSQL 로그에서 `lock_wait_timeout` 관련 로그를 확인하고, Grafana에서 DB 커넥션 대기 시간 지표를 보니 특정 계좌에 요청이 몰릴 때 잔액 업데이트 쿼리가 행 락을 획득하려고 대기하는 게 병목이었습니다. 같은 계좌에 이체가 동시에 들어오면 `UPDATE accounts SET balance = ...`가 직렬로 처리될 수밖에 없는 구조입니다. 완전한 해결보다는 병목 지점을 분석하고 원인을 파악하는 것까지 이 테스트의 목적이었습니다.

### Observability

---

**Q. Trace, Metric, Log를 각각 어떻게 활용했나?**

Trace는 OpenTelemetry로 `/api/chat` 요청 전 구간을 계측했습니다. 사용자 요청이 들어와서 쿼리 재작성, 임베딩 생성, pgvector 검색, LLM 생성까지 각 단계가 하나의 Trace 안에 Span으로 기록되고, Tempo와 Arize Phoenix로 전송해 흐름을 시각화했습니다. Metric은 Prometheus로 API 응답시간, Kafka Consumer Lag, DB 커넥션 수 등을 수집해 Grafana 대시보드로 모니터링했습니다. Log는 Pino 로거로 구조화된 JSON 로그를 남기고 Loki로 수집해 Grafana에서 Trace와 연결해서 볼 수 있게 했습니다.

---

**Q. Phoenix로 발견해서 개선한 사례?**

Prometheus가 `/api/metrics` 엔드포인트를 몇 초마다 폴링하는데, OTel HTTP 계측이 이 요청도 Span으로 기록해서 Phoenix에 분당 수백 개의 노이즈 Span이 쌓였습니다. limit=300으로 조회하면 채팅 관련 Span이 모두 이 노이즈에 밀려서 트레이스 뷰어에 데이터가 안 보이는 현상이 있었습니다. `ignoreIncomingRequestHook`으로 `/api/metrics`, `/_next/` 등을 계측에서 제외하고 나서 채팅 Span만 깔끔하게 조회됐습니다.

## 2. LLM / AI 기술 심화

---

**Q. RAG vs Fine-tuning 선택 기준?**

Fine-tuning은 모델의 일반적인 능력이나 답변 스타일을 바꿀 때 적합합니다. 반면 RAG는 최신 정보나 도메인 특화 문서를 근거로 답변해야 할 때 적합합니다. 금융 약관은 상품마다 다르고 수시로 업데이트되는데, Fine-tuning으로는 약관이 바뀔 때마다 재학습해야 합니다. RAG는 문서만 교체하면 됩니다. 또 RAG는 근거 조항을 인용할 수 있어 답변의 신뢰성을 검증할 수 있습니다. Fine-tuning이 유리한 경우는 특정 답변 형식을 일관되게 강제하거나, 도메인 용어를 모델이 아예 모르는 경우라고 생각합니다.

---

**Q. Context Window 한계 처리?**

청킹과 검색을 통해 필요한 부분만 컨텍스트로 주입했습니다. 약관 전문을 통째로 넣으면 Context Window를 초과할 뿐 아니라 LLM이 핵심 내용을 찾기 어렵습니다. top-5 청크만 주입하면 수백 자 수준으로 컨텍스트를 유지할 수 있습니다. 추가로 2단계 캐싱으로 동일하거나 유사한 질문은 LLM 호출 자체를 생략했습니다.

---

**Q. 온디바이스 LLM을 선택한 이유와 트레이드오프?**

금융 데이터는 개인정보와 거래 정보가 포함돼서 외부 API로 보내기 부담스럽습니다. LM Studio로 로컬에서 Qwen2.5-14B를 구동하면 데이터가 외부로 나가지 않습니다. 트레이드오프는 응답 속도입니다. 14B 모델을 로컬 GPU에서 돌리면 GPT-4 API보다 느립니다. 또 모델 품질도 GPT-4 수준은 아닙니다. 다만 금융 약관 QA처럼 정해진 컨텍스트 안에서 답하는 태스크는 14B 모델로도 충분하다고 판단했고, 개인정보 보호가 속도보다 중요한 우선순위라고 생각했습니다.

---

**Q. 임베딩 모델 선택 기준?**

nomic-embed-text-v1.5를 선택한 이유는 세 가지입니다. 첫째, LM Studio에서 바로 서빙이 되고 OpenAI 호환 API를 제공해서 별도 구현 없이 사용할 수 있었습니다. 둘째, 768차원으로 OpenAI text-embedding-ada-002(1536차원)의 절반이어서 저장 공간과 검색 속도에서 유리합니다. 셋째, MTEB 벤치마크에서 동급 경량 모델 중 성능이 좋은 편입니다. 한국어 특화 모델이 아니라는 한계가 있지만, 금융 약관의 주요 키워드는 모델이 의미를 충분히 잡을 수 있는 수준이었습니다.

---

**Q. Hallucination 방지를 위한 추가 안전장치?**

코사인 유사도 임계값(0.2) 외에 두 가지를 더 적용했습니다. 첫째, 컨텍스트가 없으면 "해당 내용은 제공된 약관에서 확인되지 않습니다"라고 답하도록 프롬프트를 설계했고, 컨텍스트가 있을 때는 Context 밖의 수치를 추측하지 말도록 명시했습니다. 둘째, temperature를 0.05로 설정해서 모델이 창의적으로 내용을 생성하지 못하게 했습니다. 수치가 낮을수록 같은 컨텍스트에서 일관된 답변이 나옵니다.

---

**Q. 쿼리 재작성을 도입한 이유?**

사용자들이 "중도해지하면?" 같은 구어체나 단어 수준으로 입력하는 경우가 많습니다. 이런 짧은 입력은 임베딩 벡터가 약관 문서의 벡터와 유사도가 낮게 나올 수 있습니다. LM Studio로 구어체 질문을 "중도해지 시 적용 금리 및 조건"처럼 검색에 최적화된 문장으로 변환한 뒤 임베딩하면 더 관련성 높은 청크가 검색됩니다. 다만 재작성한 쿼리는 검색에만 쓰고, 사용자에게 보이는 UI와 캐시 키는 원문 그대로 유지해서 사용자 경험에 영향을 주지 않았습니다.

## 3. 백엔드 / 아키텍처

---

**Q. DI(의존성 주입)가 왜 필요한가?**

`new`로 직접 인스턴스를 만들면 그 클래스가 특정 구현에 강하게 결합됩니다. 예를 들어 `new EmailService()`를 여러 곳에 쓰다가 SMS로 바꾸려면 모든 호출 지점을 고쳐야 합니다. DI는 의존 객체를 외부에서 주입받아서 인터페이스에만 의존합니다. 실제 구현체는 IoC 컨테이너가 결정하기 때문에 테스트할 때 Mock 객체를 주입하기 쉽고, 구현체를 교체해도 소비하는 코드를 바꾸지 않아도 됩니다. NestJS에서는 `@Injectable()` 데코레이터와 생성자 주입으로 이를 처리합니다.

---

**Q. Prisma 7에서 어댑터 방식으로 바뀐 이유?**

Prisma 7은 Edge Runtime 지원을 강화하면서 DB 드라이버를 직접 번들링하는 방식에서, 외부 드라이버 어댑터를 주입받는 방식으로 바뀌었습니다. 덕분에 Next.js Edge Runtime, Cloudflare Workers 같은 환경에서도 Prisma를 사용할 수 있게 됐습니다. 실제 프로젝트에서는 `pg` 패키지의 `Pool`을 `PrismaPg` 어댑터로 감싸서 `PrismaClient`에 주입했고, `datasource` 블록에 `url` 필드를 쓰는 대신 `prisma.config.ts`에서 연결 설정을 관리했습니다.

---

**Q. Server Component와 Client Component 구분?**

기본 원칙은 "필요할 때만 Client Component를 쓴다"입니다. DB 조회, 인증, 민감한 로직은 Server Component에서 처리하고 결과만 props로 내려줍니다. `useState`, `useEffect` 같은 React hook이 필요하거나, 브라우저 이벤트 핸들러가 필요하거나, 실시간 업데이트가 필요한 부분만 `"use client"`를 붙였습니다. 예를 들어 계좌 잔액 조회는 Server Component에서 Prisma로 바로 조회하고, 이체 폼처럼 사용자 입력을 받는 부분은 Client Component로 분리했습니다.

---

**Q. Server Component에서 Prisma 직접 호출의 장단점?**

장점은 별도 API 레이어가 없어서 코드가 단순하고, 네트워크 왕복이 줄어 응답이 빠릅니다. TypeScript 타입이 DB 모델에서 UI까지 자동으로 이어집니다. 단점은 백엔드 로직이 UI 컴포넌트에 섞여서 재사용이 어렵고, 나중에 모바일 앱 같은 다른 클라이언트를 붙이려면 API를 별도로 만들어야 합니다. 이 프로젝트는 Next.js 단일 앱이라 직접 호출이 적합했지만, 다른 클라이언트가 생길 가능성이 있으면 API 레이어를 분리하는 게 맞습니다.

---

**Q. JWT vs DB 세션 전략 선택 이유?**

DB 세션은 매 요청마다 세션 테이블을 조회해야 해서 DB 부하가 늘고, 수평 확장 시 세션 동기화 문제가 생깁니다. JWT는 서버가 토큰을 검증만 하면 되고 상태를 저장하지 않아서 서버리스나 다중 인스턴스 환경에서 유리합니다. 단점은 토큰을 강제 무효화하기 어렵다는 것인데, 이 프로젝트에서는 보안 요구사항이 복잡하지 않아서 JWT로 충분하다고 판단했습니다. 실제 금융 서비스라면 블랙리스트나 짧은 만료 시간 + Refresh Token 구조가 필요합니다.

## 4. DB / 데이터 모델링

---

**Q. `<=>` vs `<#>` 연산자 선택 이유?**

pgvector에서 `<=>` 는 코사인 거리, `<#>` 는 음의 내적입니다. 내적은 벡터 크기(magnitude)에 영향을 받아서 벡터 길이가 다르면 의미 유사도와 무관하게 크기가 큰 벡터가 상위에 올 수 있습니다. 코사인 유사도는 벡터 방향만 비교해서 크기를 정규화한 결과와 같습니다. 임베딩 모델에서 나오는 벡터는 L2 정규화가 보장되지 않는 경우가 있어서, 코사인 거리가 의미 유사도를 더 안정적으로 반영합니다.

---

**Q. Transaction에 named relation이 두 개인 이유?**

이체 거래 하나에는 출금 계좌와 입금 계좌가 모두 있습니다. `Transaction` 모델이 `Account`를 두 번 참조하는데, Prisma는 같은 모델 간 관계가 두 개 이상이면 어떤 관계인지 구분하지 못합니다. `"AccountTxns"`는 내 계좌가 소유한 거래(출금/입금), `"CounterpartyAccountTxns"`는 상대 계좌로 참조되는 거래를 명시적으로 구분한 것입니다. named relation을 쓰지 않으면 Prisma가 어떤 FK가 어떤 관계인지 ambiguous error를 냅니다.

---

**Q. 선차감 후정산 구조를 선택한 이유와 정합성 처리?**

타행이체는 처리가 완료될 때까지 몇 초에서 수십 초가 걸립니다. 이 시간 동안 잔액을 그대로 두면 사용자가 같은 돈을 두 번 쓸 수 있습니다. 그래서 이체 요청 즉시 잔액을 차감하고 상태를 `SETTLEMENT_PENDING`으로 설정합니다. 정산이 실패하면 잔액을 복원하고 상태를 `FAILED`로 변경합니다. 정합성 문제는 잔액 차감과 이체 레코드 생성을 하나의 DB 트랜잭션으로 묶어서 둘 다 성공하거나 둘 다 실패하도록 보장했습니다.

---

**Q. 인덱스 설계 기준과 pgvector 인덱스?**

일반 인덱스는 WHERE 조건에 자주 쓰이는 컬럼, JOIN에 쓰이는 FK, ORDER BY 컬럼에 우선 적용합니다. 카디널리티가 낮은 컬럼(예: 성별, 상태값 2~3개)은 인덱스 효과가 낮습니다. pgvector의 경우 이 프로젝트에서는 HNSW나 IVFFlat 인덱스를 별도로 걸지 않고 순차 스캔으로 처리했습니다. 청크 수가 수백~수천 개 수준이라 인덱스 없이도 응답 시간이 수십 밀리초 내였기 때문입니다. 수십만 개 이상이 되면 IVFFlat 인덱스를 고려해야 하는데, 그 시점에 `lists` 파라미터를 `sqrt(행 수)` 정도로 설정하는 게 일반적인 출발점입니다.
